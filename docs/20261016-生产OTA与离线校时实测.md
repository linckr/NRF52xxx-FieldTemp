## 栈诊断与新增发布阻塞

通过正常签名OTA安装CONFIG_INIT_STACKS=y诊断变体，签名镜像153204 B，SHA-256 `618d3f9ceacde33b1dc7920242c602f51ec8b12655b102ccaba87d584184e79e`。主槽完整回读一致、MCUboot不变，应用Flash152540 B（比生产候选多32 B）、RAM23016 B。测量按对应ELF识别6个栈对象，跳过各64 B MPU守卫，短时halt后finally恢复；主机采样中断不能计为连续监控。

| 栈 | 可用B | 启动后剩余B | 历史同步及OTA上传后剩余B |
|---|---:|---:|---:|
| BLE RX | 1024 | 736 | **88** |
| MPSL work | 640 | 352 | 240 |
| IRQ | 1024 | 612 | 448 |
| idle | 128 | 64 | 64 |
| main | 1024 | 248 | 248 |
| system workqueue | 1280 | 680 | 312 |

idle按现有工具默认口径单列，不能从表中隐藏。BLE RX仅88 B，低于工具128 B阈值，**运行时资源门禁不通过**；静态余1560 B不能覆盖这一风险。采集脚本“PASS”只代表读取/镜像匹配成功，不代表栈门禁通过。CFSR/HFSR为0，不能宣称已发生栈溢出。

恢复生产镜像的首次上传在confirmed23808 B、queued28000 B时等待确认偏移超时，未到END、未发TRIGGER。该失败单独保留；不能仅凭栈偏紧认定超时根因，也不能称OTA全程无异常。下一项应针对BLE RX栈预算或调用深度做独立A/B评估，并在历史/NVS/OTA负载下重复测量，不擅自降低其他栈或修改MCUboot。


生产镜像重试自27904 B续传至END校验成功，随后单独TRIGGER安装。21:00:41完整回读生产主槽153171 B匹配原候选SHA-256、MCUboot逐字不变；VTOR为应用、boot_base32401、CFSR/HFSR=0，核心SLEEPING。设备未遗留诊断镜像。完整上传后复测RX仍余88 B，system workqueue降至312 B；资源门禁依旧FAIL。

tools/stack_hwm.py同时修正为显式attach、禁自动解锁/连接暂停，拒绝接管已有暂停/异常态，自行暂停后的读取异常以finally恢复。离线故障注入验证了读取失败恢复、原暂停态拒绝及正常睡眠测量恢复三条路径。测量前仍需操作者完整核对实际镜像、ELF与INIT_STACKS配置，不能只凭版本头解释RAM。
