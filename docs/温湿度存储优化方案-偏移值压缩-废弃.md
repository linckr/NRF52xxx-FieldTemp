# 温湿度存储优化方案 - 时间戳压缩与远程配置

## 1. 概述

本文档描述了 E104-BT5010A 模块温湿度数据存储的优化方案，通过压缩时间戳并使用相对时间，并支持手机端远程配置采集间隔时间。

### 1.1 优化目标

- **内存优化**: 将单条记录从 9 bytes 压缩到 7 bytes，节省 22% 内存
- **容量提升**: 相同内存下可存储更多历史记录（约 +28%）
- **远程配置**: 支持手机端通过蓝牙配置采集间隔时间

### 1.2 硬件平台

- **芯片**: nRF52810
- **模块**: E104-BT5010A
- **传感器**: AHT30 温湿度传感器
- **SDK**: ncs 3.2.1
- **RAM 限制**: 24KB (剩余约 3.8KB 可用于数据缓存)

## 2. 时间戳压缩方案

### 2.1 原方案 vs 优化方案对比

| 字段     | 原方案             | 优化方案           | 节省              |
| -------- | ------------------ | ------------------ | ----------------- |
| 时间戳   | 4 bytes (uint32_t) | 2 bytes (uint16_t) | 2 bytes           |
| 温度     | 2 bytes (int16_t)  | 2 bytes (int16_t)  | 0                 |
| 湿度     | 2 bytes (uint16_t) | 2 bytes (uint16_t) | 0                 |
| 状态     | 1 byte             | 1 byte             | 0                 |
| **总计** | **9 bytes**        | **7 bytes**        | **2 bytes (22%)** |

### 2.2 压缩策略详解

#### 2.2.1 时间戳压缩（相对时间）

**原格式**: `uint32_t` 系统启动后的绝对秒数
**优化格式**: `uint16_t` 相对于第一条记录的间隔数

```c
// 存储格式
uint16_t time_offset;  // 间隔数（单位：采集间隔）

// 计算示例
// 假设采集间隔 = 30秒
// 第1条记录: time_offset = 0 (基准)
// 第2条记录: time_offset = 1 (30秒后)
// 第100条记录: time_offset = 99 (2970秒后)

// 实际时间 = 第一条记录时间 + time_offset × 采集间隔
```

**容量分析**:

- `uint16_t` 最大: 65535 个间隔
- 30 秒间隔: 65535 × 30 = 1,966,050 秒 ≈ **546 小时** (22.7 天)
- 60 秒间隔: 65535 × 60 = 3,932,100 秒 ≈ **1092 小时** (45.5 天)
- **完全满足需求** ✓

#### 2.2.2 温度存储（保持原值）

**格式**: `int16_t` 绝对温度值 (×100)

```c
// 存储格式
int16_t temperature;  // 温度值 (×100)

// 示例：
// 23.50°C → 2350
// -5.00°C → -500
```

**说明**: 温度保持完整精度，不进行压缩，确保数据准确性。

#### 2.2.3 湿度存储（保持原值）

**格式**: `uint16_t` 绝对湿度值 (×100)

```c
// 存储格式
uint16_t humidity;  // 湿度值 (×100)

// 示例：
// 65.00% → 6500
// 100.00% → 10000
```

**说明**: 湿度保持完整精度，不进行压缩，确保数据准确性。

### 2.3 优化后的数据结构

```c
// 缓冲区头部（存储基准时间）
typedef struct {
    uint32_t base_timestamp;    // 第一条记录的系统时间（秒）
    uint16_t record_count;      // 当前记录数
    uint16_t sample_interval;   // 采集间隔（秒）
} __packed buffer_header_t;

// 压缩后的单条记录（仅时间戳压缩）
typedef struct {
    uint16_t time_offset;      // 时间偏移（间隔数）
    int16_t  temperature;      // 温度值 (×100)，保持原值
    uint16_t humidity;         // 湿度值 (×100)，保持原值
    uint8_t  status;           // 状态标志
} __packed compressed_record_t;

// 完整缓冲区结构
#define BUFFER_SIZE 455  // 可存储约 455 条记录
typedef struct {
    buffer_header_t header;                    // 8 bytes
    compressed_record_t records[BUFFER_SIZE];  // 455 × 7 = 3,185 bytes
} __packed temp_humidity_buffer_t;
// 总大小: 3,193 bytes (~3.1 KB)
```

## 3. 时间戳管理策略

### 3.1 基准时间更新

当遇到以下情况时，需要更新基准时间：

1. **时间偏移超出范围**: `time_offset > 65535`（超过 65535 个间隔）
2. **手动触发**: 手机端发送重置基准指令
3. **缓冲区清空**: 清空缓存时重置基准时间

### 3.2 基准时间更新算法

```c
// 伪代码
if (time_offset > 65535) {
    // 更新基准时间为当前时间
    base_timestamp = current_time;

    // 重新计算所有记录的时间偏移（相对于新基准）
    for (所有记录) {
        uint32_t record_time = base_timestamp + (record.time_offset * old_interval);
        record.time_offset = (record_time - new_base_timestamp) / new_interval;
    }
}
```

### 3.3 时间戳计算

由于只压缩时间戳，温湿度保持原值，因此：

- **无需基准值管理**: 温湿度直接存储，无需基准值
- **简化实现**: 减少计算开销，提高可靠性
- **数据精度**: 温湿度保持完整精度，无精度损失

typedef struct {

**Flash 写入策略**:

- 写入前擦除对应扇区
- 使用 CRC32 校验数据完整性

## 6. 实现细节

### 6.1 数据写入流程

**重要**: 为确保时间戳精准还原，建议使用定时器严格按照间隔触发采集，而不是在任务中延迟等待。

```c
// 推荐实现：使用定时器触发采集（确保精准还原）
static void sample_timer_handler(struct k_timer *timer) {
    // 定时器中断中采集数据，确保时间精确
    int16_t temp;
    uint16_t humidity;

    // 读取传感器数据
    read_sensor(&temp, &humidity);

    // 添加到缓冲区
    add_record(temp, humidity);
}

// 定时器初始化
K_TIMER_DEFINE(sample_timer, sample_timer_handler, NULL);

void start_sampling(void) {
    // 启动定时器，每 sample_interval 秒触发一次
    k_timer_start(&sample_timer, K_SECONDS(sample_interval),
                  K_SECONDS(sample_interval));
}

// 数据写入函数
void add_record(int16_t temp, uint16_t humidity) {
    static bool first_record = true;
    static uint16_t record_index = 0;  // 使用序号而不是实际时间

    if (first_record) {
        // 第一条记录：设置基准时间
        buffer.header.base_timestamp = k_uptime_get() / 1000;
        buffer.header.record_count = 0;
        record_index = 0;
        first_record = false;
    }

    // 方法1：使用记录序号（推荐，确保精准还原）
    // 如果采集严格按照定时器间隔触发，使用序号更可靠
    uint16_t time_offset = record_index;
    record_index++;

    // 方法2：使用实际时间计算（如果采集时间可能有偏差）
    // uint32_t current_time = k_uptime_get() / 1000;
    // uint32_t elapsed = current_time - buffer.header.base_timestamp;
    // uint16_t time_offset = elapsed / buffer.header.sample_interval;

    // 检查时间偏移是否超出范围
    if (time_offset > 65535) {
        // 更新基准时间为当前时间
        buffer.header.base_timestamp = k_uptime_get() / 1000;
        record_index = 0;
        time_offset = 0;

        // 重新计算所有记录的时间偏移（可选，或标记需要更新）
        recalculate_time_offsets();
    }

    // 存储记录（温湿度保持原值）
    uint16_t idx = buffer.header.record_count % BUFFER_SIZE;
    compressed_record_t *rec = &buffer.records[idx];
    rec->time_offset = time_offset;
    rec->temperature = temp;      // 直接存储，不压缩
    rec->humidity = humidity;     // 直接存储，不压缩
    rec->status = 0;

    buffer.header.record_count++;
}
```

**精度说明**:

- **方法 1（使用序号）**: 如果采集严格按照定时器间隔触发，使用记录序号可以确保**100%精准还原**，无精度损失
- **方法 2（使用实际时间）**: 如果采集时间可能有偏差，会有精度损失（最大 `sample_interval - 1` 秒）

### 6.2 数据读取与解码

```c
void decode_record(compressed_record_t *rec,
                   uint32_t *timestamp,
                   int16_t *temp,
                   uint16_t *humidity) {
    // 解码时间戳
    // 如果使用记录序号存储（方法1），可以精准还原
    // 如果使用实际时间计算（方法2），可能有精度损失
    *timestamp = buffer.header.base_timestamp +
                 (rec->time_offset * buffer.header.sample_interval);

    // 温度直接读取（未压缩，保持完整精度）
    *temp = rec->temperature;

    // 湿度直接读取（未压缩，保持完整精度）
    *humidity = rec->humidity;
}
```

**还原精度说明**:

- ✅ **使用记录序号（方法 1）**: 如果采集严格按照定时器间隔触发，还原时间戳 = 基准时间 + 序号 × 间隔，**可以精准还原到秒级精度**
- ⚠️ **使用实际时间（方法 2）**: 如果采集时间有偏差，还原时间戳可能有误差（最大 `sample_interval - 1` 秒）
- ✅ **温湿度数据**: 无论哪种方法，温湿度数据都保持完整精度，无损失

### 6.3 配置更新处理

```c
void handle_config_write(uint8_t *data, uint16_t len) {
    if (len < 3) {
        return; // 数据长度错误
    }

    config_data_t new_config;
    new_config.sample_interval = (data[0] << 8) | data[1];
    new_config.flags = data[2];

    // 验证配置范围
    if (new_config.sample_interval < 10 ||
        new_config.sample_interval > 3600) {
        return; // 超出范围
    }

    // 更新配置
    buffer.header.sample_interval = new_config.sample_interval;

    // 如果间隔改变，需要重新计算时间偏移
    if (new_config.sample_interval != current_interval) {
        recalculate_time_offsets();
    }

    // 保存到 Flash（可选）
    save_config_to_flash(&new_config);
}
```

## 7. 性能分析

### 7.1 内存使用对比

| 项目       | 原方案  | 优化方案    | 节省 |
| ---------- | ------- | ----------- | ---- |
| 单条记录   | 9 bytes | 7 bytes     | 22%  |
| 头部信息   | 0 bytes | 8 bytes     | -    |
| 500 条记录 | 4.5 KB  | 3.5 KB + 8B | 22%  |
| 600 条记录 | 5.4 KB  | 4.2 KB + 8B | 22%  |

### 7.2 CPU 开销

- **编码开销**: 每次写入需要计算 1 个时间偏移（1 次除法和 1 次减法）
- **解码开销**: 每次读取需要 1 次乘法和 1 次加法（仅用于时间戳）
- **基准更新**: 仅在时间溢出时触发，频率极低

**结论**: CPU 开销极小，温湿度直接存储，无需额外计算

### 7.3 Flash 写入开销（配置持久化）

- **写入频率**: 仅配置变更时（通常很少）
- **擦除单位**: 1KB 扇区
- **寿命影响**: 可忽略（配置很少变更）

## 9. 注意事项

### 9.1 限制与约束

1. **温度/湿度存储**:

   - 保持完整精度，无范围限制
   - 温度: -40.00°C ~ +85.00°C (int16_t, ×100)
   - 湿度: 0.00% ~ 100.00% (uint16_t, ×100)

2. **时间偏移限制**:

   - 最大 65535 个间隔
   - 30 秒间隔 ≈ 22.7 天
   - 60 秒间隔 ≈ 45.5 天
   - 超出范围时需要更新基准时间

3. **配置间隔限制**:

   - 最小: 10 秒（保护传感器）
   - 最大: 3600 秒（1 小时）

4. **时间戳精度说明**:

   **精度损失分析**:

   当前实现使用整数除法计算时间偏移：

   ```c
   time_offset = elapsed / sample_interval;  // 整数除法，会丢失余数
   ```

   **精度损失情况**:

   - ✅ **理想情况（无损失）**: 如果采集严格按照定时器间隔触发（如每 30 秒触发一次），实际采集时间本身就是间隔的整数倍，**可以精准还原**
   - ⚠️ **有偏差情况（有损失）**: 如果采集时间有偏差（定时器不精确、系统延迟、中断延迟等），会有精度损失

   **精度损失范围**:

   - 最大损失: `sample_interval - 1` 秒
   - 例如：30 秒间隔，最大损失 29 秒（极端情况）
   - 实际损失取决于采集时间的偏差

   **示例**:

   ```
   假设采集间隔 = 30秒

   情况1（理想，无损失）:
   - 第1条: base_time = 1000秒
   - 第2条: current_time = 1030秒 (正好30秒后)
   - elapsed = 30秒, time_offset = 30/30 = 1
   - 还原: 1000 + 1×30 = 1030秒 ✓ 精准还原

   情况2（有偏差，有损失）:
   - 第1条: base_time = 1000秒
   - 第2条: current_time = 1035秒 (实际35秒后，偏差5秒)
   - elapsed = 35秒, time_offset = 35/30 = 1 (丢失5秒)
   - 还原: 1000 + 1×30 = 1030秒 ✗ 损失5秒精度
   ```

   **推荐实现**:

   - 使用定时器严格按照间隔触发采集，确保采集时间本身就是间隔的整数倍
   - 在定时器中断中采集数据，而不是在任务中延迟等待
   - 这样可以确保**精准还原**，无精度损失

5. **自定义间隔场景分析**:

   **场景 1: 固定间隔，可配置但不变** ✅ **可以压缩**

   ```
   例如：用户可以设置30秒、60秒等，但设置后固定不变
   - 使用记录序号存储，可以精准还原
   - 配置改变时重置基准时间即可
   - 推荐：使用时间戳压缩方案（7 bytes/条）
   ```

   **场景 2: 可变间隔（每条记录间隔不同）** ❌ **无法压缩，必须完整存储**

   ```
   例如：第1条到第2条间隔30秒，第2条到第3条间隔60秒，第3条到第4条间隔45秒...
   - 无法使用固定间隔计算
   - 必须存储完整时间戳（4 bytes）
   - 建议：直接使用原方案（9 bytes/条），不要压缩时间戳
   ```

   **场景 3: 间隔改变但分段固定** ⚠️ **实现复杂，不推荐压缩**

   ```
   例如：前100条是30秒间隔，后100条是60秒间隔
   - 需要分段存储，实现复杂
   - 需要存储多个基准时间和间隔
   - 建议：直接使用原方案（9 bytes/条），不要压缩时间戳
   ```

   **结论**:

   - ✅ **固定间隔（可配置但不变）**: 可以使用时间戳压缩，精准还原
   - ❌ **可变间隔**: **无法实现压缩**，必须使用完整时间戳（4 bytes）
   - 💡 **建议**: 如果间隔可能变化或每条记录间隔不同，**直接使用原方案（9 bytes/条），不要压缩时间戳**
