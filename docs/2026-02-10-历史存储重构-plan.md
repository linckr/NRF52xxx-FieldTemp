## 开发背景

- 设备在开发板上运行正常，但在目标板上出现以下现象：
  - 配置状态里显示：`历史记录数 / 存储记录数 ≈ 100+`，时间同步状态为“是”。
  - 通过历史数据接口读取 `history_info` 特性时返回：`总记录数 = 0, 起始扇区 = 0, 起始索引 = 0`。
- 说明：
  - RAM 中的 `record_count` 一直在增长。
  - W25Q64 的位置变量（`next_sector / oldest_sector / next_record_in_sector`）在当前固件下表现为“空存储”。
  - 该固件在开发板上没有问题，唯一明显差异是 **NVS 分区中已有旧数据**（位置/时间/配置等）。
- 用户希望：
  - 先确认写入是否可靠，再确认读取逻辑。
  - 历史数据读取在语义上是“线性的”（从最旧到最新，计数与读取结果一致）。

## 现状问题梳理

- **写入路径**：
  - 周期采集 -> `sample_work_handler`：
    - `record_count++`（不区分是否成功写入 Flash）。
    - 若 `err_aht == 0 && time_synced == true` 则写入 RAM 缓冲区。
    - 当 `ram_buffer_count >= RAM_BUFFER_SIZE(5)` 时调用 `storage_write_batch()`，批量写入 W25Q64。
  - `storage_write_batch()`：
    - 过滤无效数据。
    - 检查 `time_synced`、`w25q64_is_ready()`。
    - 按扇区+页对齐方式写入，多次调用 `w25q64_page_program()`。
    - 成功后更新 `next_sector / oldest_sector / next_record_in_sector`，设置 `position_dirty = true`。
- **读取路径**：
  - `history_info_char_read_cb()` 计算 `total_records / start_sector / start_record_idx`。
  - `history_char_ccc_cfg_changed()` 中计算 `history_expected_records` 作为传输总数。
  - `history_send_work_handler()` 使用 `oldest_sector / next_sector / next_record_in_sector` 做流式线性读取（按时间顺序）。
- **NVS 交互**：
  - 启动时：
    - `nvs_config_init()` -> `nvs_load_config()` -> 加载采集间隔等配置。
    - `nvs_load_storage_position()` -> 填充 `next_sector / oldest_sector / next_record_in_sector`。
    - `nvs_load_time()` -> 可能直接将 `time_synced` 置为 true。
    - `storage_init()` -> 使用 NVS 中的位置做“写头校验 + 二分/线性恢复”。
  - 运行中：
    - 写入成功后仅设置 `position_dirty = true`。
    - 通过 `local_nvs_flush()` + `nvs_save_storage_position()` 定期写入 NVS。
- **潜在问题点**：
  - `history_info_char_read_cb()` 里总记录数计算公式复杂且与 `history_expected_records` 不一致，易出错。
  - 位置恢复逻辑依赖 NVS 中的旧值，如果芯片上之前写入的是旧格式数据（或已经被其他固件改写），可能导致“看起来为空”或计数异常。
  - `status` 特性中的 `record_count` 并不是真实的“已存入 Flash 的记录数”，容易误导上层 UI。

## 本次重构目标

1. **总记录数语义清晰且可重复**：
   - 使用一套统一的逻辑计算“当前可读取的有效记录数”，在以下位置保持一致：
     - `history_info_char_read_cb()` 返回的 `total_records`。
     - 历史传输模块内部的 `history_expected_records`。
   - 避免“同一份存储位置用两套公式计算，结果不一致”的情况。
2. **读取逻辑语义线性**：
   - 明确约定：读取次序始终为“从 `oldest_sector:0` 开始，按扇区顺序线性读取到 `next_sector:next_record_in_sector`”。
   - 有时间戳过滤时，仅在“线性顺序”上跳过不符合条件的记录，不再做复杂的扇区级二分推断。
3. **降低 NVS 脏数据的破坏性**：
   - 启动时如果从 NVS 读到的位置与 Flash 实际状态不匹配，能够自动纠正到一个“自洽的写头位置”，而不是让历史接口一直返回 0。
   - 保持与现有 NVS key 基本兼容，但在逻辑上更鲁棒。
4. **保证与开发板行为一致**：
   - 不破坏当前在开发板上“工作正常”的行为。
   - 尽量做到：如果 Flash + NVS 是纯净/自洽的，重构后行为与之前完全一致；只有在“有脏数据/矛盾数据”时才做更安全的修正。

## 设计方案（MVP）

### 1. 统一总记录数计算函数

- 在 `main.c` 中新增一个内部函数：
  - 输入：`next_sector / oldest_sector / next_record_in_sector`。
  - 输出：`uint32_t total_records`。
- 逻辑：
  - 若 `next_sector == oldest_sector`：
    - 直接返回 `next_record_in_sector`（0 表示无数据，>0 表示所有数据都在一个扇区）。
  - 否则：
    - 计算扇区距离（环形）：  
      `sector_count = (next_sector > oldest_sector) ? (next_sector - oldest_sector) : (W25Q64_MAX_SECTORS_LIMIT - oldest_sector + next_sector)`
    - 总记录数：`total_records = (uint32_t)sector_count * W25Q64_RECORDS_PER_SECTOR + next_record_in_sector`。
- 使用场景：
  - `history_info_char_read_cb()`：只负责打包返回值，不再手写计算公式。
  - `history_char_ccc_cfg_changed()`：设置 `history_expected_records` 时复用同一个函数。
  - `storage_init()` 完成写头定位后打印一条“总记录数估算”日志，便于串口诊断。

### 2. 保持线性读取语义

- 当前 `history_send_work_handler()` + `linear_find_first_after_timestamp()` 的读取逻辑，实际上已经是“按扇区+记录索引线性扫描”的模式：
  - 从 `oldest_sector` 开始，扇区内从 0 到 `max_records_in_sector` 递增。
  - 在最后一个扇区使用 `next_record_in_sector` 作为有效记录上限。
  - 碰到 `timestamp == 0xFFFFFFFF` 或其他异常时，做安全跳过。
- 本次重构只做两点约束强化：
  - 所有“完成条件”的判断都依赖统一的“总记录数/写头位置”逻辑，不再引入额外推断。
  - 确保“从起始扇区和起始索引开始”后，只通过简单的“前进索引 + 扇区轮转”来遍历全部数据。

### 3. NVS 影响与处理策略

- NVS 目前的作用：
  - 存储：`next_sector / oldest_sector / next_record_in_sector`（位置元数据）。
  - 存储：时间基准 `time_base_timestamp`（决定 `time_synced` 启动状态）。
  - 存储：配置（采集间隔、历史最高/最低温度等）。
- 差异来源：
  - 开发板：通常是**干净/新刷写**的 NVS + Flash。
  - 目标板：可能曾运行过旧固件，NVS 中残留旧版本位置/配置/时间，导致：
    - `next_sector / oldest_sector / next_record_in_sector` 与当前 Flash 布局不一致。
    - `storage_init()` 在校验写头时读到“看似 0xFF/空”的位置，从而错误判断“无数据”。
- 本次重构对 NVS 的处理（MVP）：
  - **不修改 NVS key 结构**，保持函数接口不变：
    - `nvs_load_storage_position()` / `nvs_save_storage_position()` / `nvs_clear_storage_position()`。
  - 在 `storage_init()`：
    - 继续使用当前的“根据 NVS 位置 + Flash 实际内容做校验/二分修正”的逻辑。
    - 在最终确定写头位置后，使用统一的“总记录数计算函数”估算当前有效记录数，并打印：
      - `[存储] 写头定位完成 next=... oldest=... rec=... -> 总记录数=...`
    - 如果估算结果为 0，但 NVS 中位置并非全 0 且 Flash 读取出现异常，则视为“位置元数据已损坏”，可以后续视需求加开关做一次性 `nvs_clear_storage_position()`。
  - 结合手机端“清空数据”操作（已有）：
    - 当用户在 UI 中执行“清空数据”时，固件会擦除 W25Q64 对应分区并调用 `nvs_clear_storage_position()`，把位置状态重置为干净，彻底消除历史 NVS 脏数据影响。

### 4. 后续可选增强（暂不在本次 MVP 中实现）

- 新增一个持久化的“历史总记录数”字段（如 `NVS_ID_TOTAL_RECORDS`），避免每次只靠位置推算。
- 状态特性中拆分：
  - `record_count`：本次上电采集次数。
  - `stored_count`：当前 W25Q64 中实际可读取的记录数（与 `history_info` 一致）。
- 在检测到“位置明显非法”（如扇区索引超范围、多次校验失败）时，自动触发一次性 Flash+NVS 清理逻辑，仅保留本次之后的新数据。
