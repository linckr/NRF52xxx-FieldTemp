# 2026-10-15 独立上电离线记录诊断

## 已取得证据

- 用户约06:30装入电池看到启动闪烁，约15:00首次连接；电池未主动拔出。
- 实际手机是realme，安装App1.1.0/code2 Debug、Room10；此前1.1.4正式版验收设备是小米。原始数据库/WAL/设置已完整本机留档，活动3939条、SQLite integrity ok，未写回或清理。
- SWD最终只读主槽152362 B，SHA256与正式1.0.11完全匹配；Flash/NVS/蓝牙当前就绪、CFSR/HFSR为0。首次多次No ACK与一次电脑BLE服务发现中断不是历史已丢失的证明。
- 1MHz完整外部存储读取1236992 B、93.14秒。暂停前保存RAM/寄存器，恢复后继续运行；没有复位或擦写Flash。原始文件和SHA256留在本机，不入库。
- 按暂停时RAM中的逻辑首记录、实际写头和count，逐槽解析有效环**4324条**；不是全物理区域扫描后混入已回收记录。检查点head允许滞后，使用实际next_sector/next_record求当前写头，并校验与count完全一致。

## 数据在哪里

物理顺序3406–3925有**520条**连续约8小时18分钟的记录，存储时间为**10月14日15:19:17–23:37:17**，温度**20.91–28.32°C**、气压**964.71–1018.94 hPa**。这些值/时长符合骑行离线数据特征，520条的时间戳、温湿度、气压均已在realme数据库逐条匹配，并非520条没有同步。

其后物理顺序3926开始直接跳至**10月15日15:03:00**，与手机下午对时后恢复真实日期相符。数据库“今天”只有两条带GPS手机采样，按日期看不到前述520条。因此本次主要证据支持**记录被写入错误日期，再按错误日期展示**；不能把它归咎于只需升级App就解决，也不能再称本次520条被增量同步漏掉。

## 代码根因

1. `nvs_load_time`将上次手机对时值作为可用时间返回。
2. main冷启动把该旧值设为time_base_timestamp，把新启动uptime设为time_base_uptime，并置time_synced=true；wall_clock_aligned=false只改变对齐方式，没有修正绝对时间。
3. 之后按旧基准加本次运行时长落盘。NVS只保存一个旧墙钟值，没有持续计时的外部RTC，也不能知道停机时长。
4. 手机对时只改变未来记录和聚合窗口，不回写已有历史，所以旧日期记录不会自动移动到今天。
5. 缺少有效NVS时间时，time_synced=false，采样不会聚合成历史。这是另一种会真正没有历史的冷启动情况；本次520条存在，不应混为一谈。

上电三秒闪烁在Flash/传感器/蓝牙初始化之前发生，只证明进入应用，不能证明后续全部运行正常。

## 另一个独立问题：存在重启

首次成功抓取时kernel curr_tick对应本次启动约65秒、wall_clock_aligned=false，NVS恢复的是下午15:02:36基准；这次成功读取没有halt/reset/write。原始历史还出现16:30:00→15:03:37及20:06:37→15:03:37两处回退，后一处与现场近期重启一致。用户没有主动拔电池不等于从未复位；可能涉及电池座接触、欠压、其他复位原因，目前不能唯一归因，也没有证据说是这次只读SWD导致复位。

## 恢复边界与预览

520条原记录保留不动。本机另有校正预览CSV，以“最后旧时间记录距下午15:02:36对时不超过60秒、该连续段没有额外停机、时钟速率可信”为条件估算区间；在该假设下首条约06:43:36–06:44:36。**这不是已恢复的真实时间**，也不能直接强行把首条定成用户约06:30。事件记录、实际首次采样时间、RC误差、未观测到的停机可能扩大不确定性。需要用户确认校正策略后才能应用，当前没有修改手机或模块记录。

## 下一步建议

- 当前固件临时使用方式：每次重新上电后先连App对时，再离线使用。意外复位仍会重新产生旧时间问题。
- 近期应单独设计离线时间修复：区分本次启动时间可信度，保存启动会话/相对时间，首次对时后按明确会话补齐；需要同时审查App、协议、数据迁移及Flash/RAM成本，不能直接全库平移。
- 产品若要求任意断电后无需手机即可准确记录绝对时间，需要持续供电RTC或其他可信时间源；仅保存更多NVS墙钟值不能知道任意断电时长。
- 对重启原因另行取证，先检查已知CR2032接触问题、负载电压和复位证据，不能用一次启动闪烁替代持续运行验证。
